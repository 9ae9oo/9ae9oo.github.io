01

강조색을 글자색으로 쓰는 25곳이 전부 대비 1.6~2.0:1 — 선택된 것이 가장 안 보인다

심각중간
지금 상태
파스텔 --accent 하나가 면(배경·테두리)과 글자 양쪽에 쓰입니다. 활성 탭, 좌측 레일의 현재 페이지, 재생 중인 곡, 토요일 날짜가 모두 이 색 글자라 흰 카드 위에서 1.63~2.03:1 입니다.
왜 문제
사용자가 가장 확실히 읽어야 할 "지금 선택된 것"이 주변 항목보다 흐리게 보이는 역전이 일어납니다. 프리셋을 바꿔도 5종 전부 미달이라 우연이 아니라 구조 문제입니다.
대안
--accent는 면·테두리·밑줄 전용으로 두고, 글자용 --accent-ink를 파생시킵니다. js/shell.js의 applyTheme에서 이미 쓰는 U.mixHex로 흰 배경 대비 4.5:1을 넘길 때까지 어둡게 섞으면 됩니다(base #9db8f0 → 약 #3f63b4). 새 색·새 장식 없이 토큰 하나만 늘어납니다.
02

의미색(초록·빨강·주황)이 다크 전용 값 한 세트뿐 — 흰 카드 위 금액·경고가 1.5~1.9:1

심각작음
지금 상태
실제로 켜지는 테마는 라이트 프리셋 5종뿐인데 --green #4ade80, --red #f87171, --amber #fbbf24는 어두운 배경 기준 값입니다. MONEY의 21px 볼드 금액이 1.7:1, 일정 알람 헤더가 1.51:1입니다.
왜 문제
돈·경고·완료처럼 정확히 읽혀야 하는 정보가 화면에서 가장 안 보이는 글자가 됐습니다. 토스트 경고는 1.44:1로 배경과 거의 붙습니다.
대안
:root[data-preset] 공통 블록에 흰 배경용 진한 값을 추가합니다 — --green #15803d(5.0:1), --red #b91c1c(6.5:1), --amber #a16207(4.9:1). -dim 배경 알파는 그대로 두면 되므로 "옅은 배경 + 진한 글자"가 되어 칩·콜아웃·알람이 그대로 읽힙니다.
03

--text-dim이 모든 팔레트에서 AA 미달인데 60곳 넘게 쓰임 — WORKFLOW 컷 숫자 포함

심각작음
지금 상태
2.20~3.21:1. 이 앱의 주 컨텐츠인 체크보드의 미완료 컷 숫자가 2.82:1이라 격자가 "숫자가 적힌 칸"이 아니라 "거의 빈 회색 칸"으로 보입니다.
왜 문제
완료 칸(8.9:1)과 미완료 칸의 대비 격차가 3배가 넘어, 진행 상황을 훑을 때 미완료 쪽 숫자를 읽으려면 눈을 붙여야 합니다. 게다가 9.5~11px 초소형 글자에도 같은 색을 써서 크기와 대비가 동시에 최저치입니다.
대안
--text-dim을 #949aa8 → #6f7686로 내립니다(흰 배경 4.55:1). --text-muted와는 여전히 구분되므로 3단 위계는 유지됩니다. 여기에 규칙 하나를 더합니다 — 11px 미만 글자에는 dim을 쓰지 않고 muted를 쓴다.
04

프리셋 5개 전부 --surface-0과 --surface-1이 같은 색 — 표면 위계가 존재하지 않는다

심각중간
지금 상태
코드는 surface 0→1→2 세 단계를 전제로 짜여 있는데, 출고되는 5개 테마에서 0단과 1단이 물리적으로 같은 픽셀 값입니다.
왜 문제
"그림자 없이 색과 타이포로 위계를 표현한다"고 정해놓고, 정작 위계를 담당할 표면 토큰이 무너져 있습니다. 카드·입력창·비활성 칸이 전부 한 장의 흰 판이 되고 남은 구분 수단은 1.24:1 테두리 한 줄뿐입니다. 거래 표의 고정 헤더가 본문 행과 같은 배경이라 스크롤 중 섞이고, 설정에서 카드색을 바꾸면 안쪽 흰 요소들이 구멍처럼 남습니다.
대안
프리셋의 --surface-0를 카드보다 한 단계 눌린 값으로 실제 분리합니다(base #f7f8fc / mint #f4faf7 / peach #fdf7f3 / lavender #faf7fe / butter #fbf8ef). 그리고 설정의 카드색 노브는 --surface-1만 바꾸는 대신 U.mixHex로 표면 스케일 전체를 파생시킵니다.

05

CSS 전체에 :focus-visible이 0건 — 키보드로는 지금 어디 있는지 알 수 없다

심각작음
지금 상태
입력창은 outline: none으로 기본 링을 지우고 대체 신호가 테두리 색 변화 하나뿐인데 그 변화가 1.99:1입니다. 버튼·탭·컷 칸은 OS 기본 링에 의존해 요소마다 표시가 제각각입니다. Tab으로 체크보드를 지나가면 100개 넘는 칸을 통과하는데 어디인지 알 수 없습니다.
왜 문제
키보드 사용자에게는 현재 위치 표시가 사실상 없는 상태이고, 색상 변화 하나에만 의존하므로 색각 이상 사용자에게도 마찬가지입니다.
대안
전역 규칙 한 줄: :focus-visible { outline: 2px solid var(--text); outline-offset: 2px; }. --text는 흰 배경 15:1이라 프리셋 5개 전부에서 확실히 보이고 강조색 밝기에 좌우되지 않습니다. :focus-visible은 마우스 클릭에는 걸리지 않으므로 지금의 조용한 화면은 그대로입니다.
06

비활성 입력창이 활성과 픽셀 단위로 동일 — .field:disabled 규칙이 없다

심각작음
지금 상태
설정 → 음악에서 재생목록이 없으면 주소 입력창이 비활성인데 겉보기엔 멀쩡합니다. 같은 줄의 버튼만 42%로 흐려져서, 버튼은 죽고 입력창은 살아 있는 모순된 화면이 됩니다. 비활성 투명도도 0.42 / 0.25 / 없음 세 갈래입니다.
왜 문제
사용자가 주소를 붙여넣고 왜 아무 일도 안 일어나는지 찾게 됩니다. 게다가 opacity로 만든 비활성(2.43:1)이 평범한 보조 텍스트와 밝기가 완전히 겹쳐, 흐린 정도만으로는 비활성인지 부가 정보인지 구분할 수 없습니다.
대안
--disabled-opacity: 0.42 토큰을 만들어 세 곳을 통일하고 .field:disabled { opacity: var(--disabled-opacity); cursor: not-allowed; } 한 줄을 추가합니다. input·select·textarea 전부에 한 번에 적용됩니다.
07

선택하면 hover가 죽고, 선택 표시 문법이 4갈래로 갈린다

심각중간
지금 상태
상태 규칙이 :hover보다 뒤에 선언돼 있어, 체크된 컷·완료한 해빗·재생 중인 트랙 위에 마우스를 올리면 아무 반응이 없습니다. 좌측 레일의 현재 페이지 표시는 1.10:1 배경 하나뿐인데, 마우스를 올리면(1.16:1) 오히려 더 진해지는 역전까지 있습니다.
왜 문제
체크한 컷을 다시 눌러 해제하는 것이 WORKFLOW의 핵심 조작인데, 하필 되돌릴 수 있는 요소에서만 hover가 죽어 헛클릭을 유발합니다.
대안
선언 순서를 "기본 → 상태 → 상태+hover"로 못박고 .cut.on:hover 같은 조합 규칙을 명시합니다(--accent-hover는 이미 존재하는 토큰). 선택 표시는 색 대신 명도 계단 + 굵기로 통일합니다 — 배경 --surface-3, 글자 --text/600, accent는 2px 밑줄 같은 "선"에만.

1차 내비게이션 아이콘 9개가 전부 컬러 이모지 — hover·active 색 규칙이 통째로 죽어 있다

심각큼
지금 상태
사이드바 5개(🏠🎬📅💰⚙️)와 툴레일 4개(📥📝🎵⏱️)가 컬러 이모지입니다. 컬러 폰트는 자기 색을 칠하므로 color 선언이 아무 효과가 없습니다.
왜 문제
이미 작성해 둔 3단계 색 규칙(--text-muted → --text → --on-accent)이 화면에 전혀 나타나지 않습니다. 테마를 5개나 만들어 두고 앱에서 가장 눈에 띄는 요소만 그 테마 밖에 있습니다. 메모 카드에서는 ♥(텍스트)만 상태색이 먹고 🔒·🗑(이모지)는 죽는 반쪽 동작까지 생깁니다.
대안
js/util.js에 U.icon(name) 헬퍼를 두고 currentColor 인라인 SVG로 교체합니다. js/timer.js에 이미 createElementNS로 SVG를 만드는 패턴이 있어 외부 라이브러리 없이 단일 파일 빌드도 그대로 통과합니다. 규격은 viewBox="0 0 24 24", stroke="currentColor", stroke-width="1.75"로 고정.
09

BGM 재생 버튼과 다음 곡 버튼이 똑같은 글자 ▶ — 크기 2px 차이로만 구분된다

심각중간
지금 상태
미니바에서 11px ▶(다음 곡)과 14px ▶(재생)이 2px 간격으로 붙어 있습니다. 같은 줄에 컬러 이모지(🔀🔁🔇🔊)와 단색 글리프(◀▶❚❚)가 섞여 있고, .mus-control.on의 강조색은 이모지 쪽에서만 무효입니다.
왜 문제
플레이어의 가장 기본적인 두 동작을 눌러보기 전에는 구분할 수 없습니다. 표준 플레이어라면 형태 자체가 다른데(다음 곡 = 삼각형 + 세로 바) 여기서는 형태 정보가 아예 없습니다. 셔플·음소거가 켜졌는지도 색으로 표시되지 않습니다.
대안
transport 5개를 SVG로 바꿔 형태로 구분합니다 — 재생 M8 5v14l11-7z, 일시정지는 사각형 두 개, 다음 곡은 삼각형+세로 바, 이전 곡은 좌우 반전. 크기는 .mus-control svg { width:18px } 한 줄로 모읍니다.

4군 — 토큰이 기준으로 작동하지 않음

10

버튼 높이가 5종(20·22·27·30·36px) — 36px 입력칸 옆에 27px 버튼이 붙는다

심각중간
지금 상태
작품 선택 드롭다운(36px) 옆의 [작품 관리]가 27px, 작품 이름 입력칸(36px) 옆의 [작품 추가하기]가 27px입니다. 세로 가운데 정렬이라 위아래로 4.5px씩 틈이 생깁니다. 정작 토큰 --control-inline-h: 32px는 정의만 되고 사용처가 0회입니다.
왜 문제
같은 .btn-sm이 WORKFLOW에서만 22px, 다른 페이지에서는 30px로 렌더돼 화면을 옮기면 버튼이 한 단계 커집니다. 작품 관리 모달 하나 안에서만 22 / 30 / 36px 세 높이가 세로로 놓여 정렬선이 세 번 어긋납니다. 쓰이지 않는 토큰이 남아 있다는 것 자체가 "토큰을 안 보고 새 숫자를 적었다"는 증거입니다.
대안
단계를 셋으로 확정합니다 — --control-h 36px(입력칸과 같은 줄), --control-sm-h 30px(보조), 신규 --control-xs-h 22px(텍스트 줄에 얹히는 인라인). 27px·20px은 22px로 흡수하고 죽은 --control-inline-h는 삭제합니다. 입력칸과 같은 줄에 서는 버튼들은 오버라이드를 지워서 36px을 그대로 쓰게 합니다.
11

모서리 값이 15종 — 토큰과 똑같은 6px·10px까지 손으로 다시 적혀 있다

보통중간
지금 상태
토큰은 --radius 10px, --radius-sm 6px 둘뿐인데 실제로는 2·3·4·5·6·7·9·10·11·12·16·17·999px·50%가 쓰입니다. BGM 패널만 11~17px 계열을 혼자 쓰고, 공정 헤더 한 줄에 999px·6px·4px이 동시에 있습니다.
왜 문제
Inbox → Memo → BGM을 번갈아 열면 BGM만 다른 앱에서 가져온 화면처럼 보입니다. 컷 격자는 카드(6px) 안에 7px 칸이 들어가 바깥보다 안쪽이 더 둥근 역전이 생기고, 모바일에서는 9px로 더 벌어집니다. 알약(999px)은 원래 상태 배지의 모양인데 버튼이 빌려 쓰면서 "누르는 것 / 읽는 것"의 구분이 흐려집니다.
대안
--radius-xs 3px를 추가해 xs/sm/lg 세 단계 + 999px(배지 전용) + 50%(원)로 정리하고, 6px·10px 하드코딩 7건을 토큰 참조로 치환합니다. 컷 칸의 7px/9px은 var(--radius-sm)로 통일합니다(손가락 타깃은 칸 크기로 이미 해결됨).
12

font-size가 23종이고 27개 선언이 0.5px 단위 — 없는 굵기 750·650도 쓰고 있다

심각중간
지금 상태
9 / 9.5 / 10 / 10.5 / 11 / 11.5 / 12 / 12.5 / 13 / 13.5px이 0.5px씩 붙어 있어 서로 구분되지 않습니다. font-weight: 750·650은 로드된 Pretendard에 없는 굵기라 각각 800·700으로 튀어 렌더됩니다. 그 결과 회차 제목(22px/750→800)이 페이지 제목(21.6px/700)보다 크고 무거워 위계가 뒤집힙니다.
왜 문제
"작은 글씨"가 필요할 때마다 새 값이 하나씩 늘어난 흔적이고, 스케일이 아니라 목록입니다. 한글 표 헤더에 걸린 text-transform: uppercase는 한글에 아무 효과가 없어 죽은 코드이고, 함께 딸려온 자간만 벌어져 라벨이 성기게 보입니다.
대안
--fs-xxs 11px ~ --fs-xl 20px 7단계로 접고 0.5px을 전부 없앱니다(11px = 한글 가독 하한). 750→700, 650→600으로 교정하고, 한글 라벨의 uppercase와 letter-spacing은 삭제합니다. line-height도 12종 → 4단계(1 / 1.35 / 1.5 / 1.7)로 접습니다.
13

간격의 64%가 4px 격자 밖 — 같은 역할의 카드에 padding이 9종

보통큼
지금 상태
7px 43곳, 9px 20곳, 11px·13px 각 11·12곳. 표면·테두리가 사실상 같은 카드인데 안쪽 여백만 16 / 14·16 / 11·12 / 12 / 11·13 / 14 / 10 / 8 / 7·8 아홉 갈래입니다. MONEY 한 화면을 스크롤하면 그중 다섯 종류를 연속으로 지나갑니다.
왜 문제
1~2px 차이는 개별로는 버그로 보이지 않지만, 화면 전체가 "어딘가 흐릿하게 안 맞는" 느낌으로 누적됩니다. 탭 아래 첫 블록까지의 거리도 화면마다 10 / 14 / 18px이라 페이지를 옮길 때 리듬이 바뀝니다.
대안
--sp-1 4px ~ --sp-6 24px 계단과 --card-pad 16px / --card-pad-sm 12px 두 개만 정의하고 기계적으로 치환합니다. 5·6·7 → 4 또는 8, 9·10·11 → 8 또는 12, 13·14·15 → 12 또는 16.

사이드 패널이 콘텐츠를 밀어내지 않고 덮는다 — 1554px 미만에서 카드 오른쪽이 잘린다

심각큼
지금 상태
#panelhost가 position: fixed라 흐름 밖이므로 #content는 전혀 줄지 않습니다. 1440px에서 57px, 1280px에서 137px이 덮입니다. 그런데 css/shell.css·index.html·js/shell.js 세 곳의 주석은 모두 "패널이 열리면 메인이 그만큼 줄어든다"고 반대로 적혀 있습니다.
왜 문제
노트북 해상도에서 Inbox·Memo·Music·Timer를 열 때마다 콘텐츠 오른쪽이 가려집니다. 게다가 좌우 레일이 서로 다른 언어(왼쪽은 콘텐츠에 붙은 56px 둥근 카드, 오른쪽은 화면 끝에 붙은 41px 반쪽 탭)라 카드가 이미 중앙에서 37px 밀려 있어 겹침이 더 커집니다. 641~874px 구간에서는 레일이 카드 위를 26px 덮습니다.
대안
우측 레일을 #app의 flex 자식으로 되돌려 [56][18][콘텐츠][18][56] 대칭을 만들고, #panelhost는 flex-basis 전환으로 바꿔 실제로 콘텐츠를 밀게 합니다. 그러면 주석이 설명하는 동작과 코드가 일치하고 중간 폭 겹침도 자동으로 사라집니다.

캘린더가 뷰포트 기준 브레이크포인트라, 넓은 모니터에서 하루 칸이 49px

심각중간
지금 상태
페이지 안쪽 폭은 660px인데 .cal-layout은 1fr + 300px 2단을 유지합니다. 1단으로 접는 분기가 @media (max-width: 1000px)라 뷰포트 기준이어서 1920px 모니터에서는 절대 발동하지 않습니다.
왜 문제
화면이 아무리 넓어도 월간 달력은 49px짜리 칸에 일정을 두세 글자로 잘라 넣습니다. 셸은 콘텐츠 폭을 800px로 제한하는데 페이지 CSS는 화면 폭을 보고 판단해서, 두 기준이 서로 다른 세계를 봅니다.
대안
이미 work.css가 쓰고 있는 방식을 그대로 옮깁니다 — .page { container-type: inline-size } + @container (max-width: 700px). 그러면 콘텐츠 폭 프리셋을 어떻게 바꿔도 달력이 스스로 접힙니다.

"탭" 역할에 시각 언어 6종 — MONEY 한 페이지에 밑줄·알약·박스가 3층으로 쌓인다

심각중간
지금 상태
1차는 밑줄 탭, 2차는 알약 탭, 3차는 박스 탭이 세로로 붙어 나옵니다. 선택 표현도 밑줄 / 옅은 배경+테두리 / 진한 배경+반전 글자 세 종류입니다.
왜 문제
계층 깊이가 모양에서 읽히지 않고, 오히려 3차 탭이 2차 탭보다 무거워 보입니다. "이 중 하나를 고른다"는 같은 의미가 화면마다 다른 신호로 나타납니다.
대안
계층별로 하나씩만 남깁니다 — 1차 .tabs(밑줄, 현행 유지), 2차 .subtab, 3차/모드 선택 .seg. .cal-views와 .todo-tab은 삭제하고 각각 .seg·.subtab으로 치환합니다.

선이 과하다 — 접힌 카드 아래 2px 이중선, 모달 안 상자 4겹, 여백으로 충분한 자리의 가로선

심각작음
지금 상태
공정을 접으면 헤더의 border-bottom과 카드 자신의 아래 테두리가 틈 없이 붙어 그 카드만 아래 선이 2px가 됩니다. 작품 관리 모달은 "모달 → 목록 상자 → 행 → 미니 태그"로 테두리가 4겹이고, 회차가 20개면 그 안에서만 19개의 가로선이 그어집니다.
왜 문제
공정을 접어두고 쓰는 것이 기본 사용 방식이라, 펼친 카드(1px)와 접은 카드(2px)가 나란히 놓이면서 선 굵기가 카드마다 들쭉날쭉해 보입니다. 게슈탈트 근접성 관점에서 이미 여백·라벨·색으로 그룹이 표현된 자리에 선을 한 번 더 긋고 있습니다.
대안
.proc-head:last-child { border-bottom: 0 } 한 줄로 이중선은 즉시 해결됩니다. 더 나아가 헤더 구분선 자체를 없애고 .proc-body의 위 여백을 4px 늘리면 카드 개수만큼 가로선이 사라집니다. 모달 회차 목록은 border-bottom 대신 gap: 2px로 나눕니다.

정해야 할 것 두 가지 — 그림자 19곳, 그리고 아무도 못 보는 다크 팔레트

보통작음
지금 상태
AGENTS.md에는 "그림자·입체감 없이"라고 적었는데 실제 CSS에는 box-shadow가 25건 있고, 그중 8건은 토큰을 우회한 하드코딩입니다(검정 계열과 네이비 계열 두 갈래). 한편 tokens.css의 :root에는 완전한 다크 팔레트가 정의돼 있는데, 설정의 테마 프리셋은 5개 전부 라이트이고 data-theme도 붙지 않아 UI에서 도달할 방법이 없습니다.
왜 문제
원칙과 코드가 어긋난 채로 두면 다음에 누가 그림자를 더해도 근거가 없습니다. 다크 팔레트는 "있지만 안 보이는 코드"라 유지보수 때마다 판단을 흐리고, 실제로 의미색이 다크 기준으로만 정의된 원인(02번)이기도 합니다.
대안
둘 다 결정이 먼저입니다. 그림자는 ① 전부 제거하고 테두리로 통일 ② "떠 있는 것(패널·모달·토스트·미니바)에만 var(--shadow) 허용" 규칙을 AGENTS.md에 명시 — 둘 중 하나를 고르고 하드코딩 8건은 어느 쪽이든 토큰으로 모읍니다. 다크 팔레트는 프리셋에 다크를 추가해 살리거나, 안 쓸 거면 삭제해 라이트 기준으로 정리합니다.
